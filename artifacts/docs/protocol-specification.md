# Спецификация протокола обмена данными (Protocol Specification) v1.1

Настоящий документ описывает «контракт» между компонентами системы: формат данных, правила упаковки, передачи и обработки информации на всех уровнях: от радиоканала ESP-NOW до проводного интерфейса UART.

## История изменений (v1.0 -> v1.1)
1. **Удален CRC из строки ESP-NOW.** Аппаратный уровень ESP-NOW уже защищает пакет от помех. Дублирование CRC в строке неоправданно расходует место в пакете (до 250 байт).
2. **Добавлен `CMD_ID` в пакет команды.** Это необходимо для корректного связывания команды и её подтверждения (ACK).
3. **Указан точный алгоритм CRC16.** Для совместимости ESP32 и Python зафиксирован стандарт **CRC-16/CCITT-FALSE**.
4. **Время заменено на Unix Timestamp.** Вместо строки `12:00:01` (которая не содержит даты) используется целое число (количество секунд с 1 января 1970 года).
5. **Уточнен процесс валидации.** Разделена проверка целостности кадра UART и логическая валидация данных.

---

## 1. Общие принципы (Соглашение)

1. **Кодировка:** Все текстовые данные передаются в кодировке **ASCII**.
2. **Разделитель:** В качестве разделителя полей используется символ **пробел (0x20)**.
3. **Пустые поля:** Если значение отсутствует (например, датчик неисправен), передаются два пробела подряд.
4. **Контроль целостности:** На уровне UART используется алгоритм **CRC-16/CCITT-FALSE** (Полином: `0x1021`, Начальное значение: `0xFFFF`, без отражения).
5. **Время (Timestamp):** Используется целое число (Unix Timestamp) — количество секунд, прошедших с 1 января 1970 года. Пример: `1714132801`. (Если ESP32 не имеет модуля RTC, узел передает `0`, а сервер подставляет `NOW()` в момент получения).
6. **Регистр:** Заголовки (TLM, CMD, ACK) всегда заглавными буквами.

## 2. Уровень 1: Радиоканал ESP-NOW

Обмен по ESP-NOW происходит строками. Максимальный размер полезной нагрузки — 250 байт.

### 2.1. Пакет телеметрии (Узел -> Концентратор)
Формат строки: 
`[HEADER] [DEV_ID] [TOPIC] [TIMESTAMP] [SCHEMA] [VAL_1] ... [VAL_N]`

*   **HEADER:** Всегда `TLM`.
*   **DEV_ID:** Идентификатор устройства (например, `01`).
*   **TOPIC:** Имя таблицы/маршрутный ключ (например, `sensors`).
*   **TIMESTAMP:** Время формирования посылки (Unix Time, например, `1714132801` или `0`).
*   **SCHEMA:** Версия схемы данных (например, `v1`).
*   **VAL_1 ... VAL_N:** Значения полей (от 1 до 16). Разделены пробелами.

**Пример (2 датчика):**
`TLM 01 sensors 1714132801 v1 25.5 61.8`

**Пример (1 поле пустое):**
`TLM 02 boiler 1714132805 v1 80.0  1.2` *(два пробела между 80.0 и 1.2)*

### 2.2. Пакет команды (Концентратор -> Узел)
Формат строки:
`[HEADER] [DEV_ID] [CMD_ID] [CMD_TYPE] [ARG_1] ... [ARG_N]`

*   **HEADER:** Всегда `CMD`.
*   **CMD_ID:** Уникальный ID команды (генерируется сервером/хабом), нужен для ACK.
*   **CMD_TYPE:** Тип команды (например, `set_interval`, `reboot`).

**Пример:**
`CMD 01 42 set_interval 30`

### 2.3. Пакет подтверждения (Узел -> Концентратор)
Формат строки:
`[HEADER] [DEV_ID] [CMD_ID] [STATUS]`

*   **HEADER:** Всегда `ACK`.
*   **STATUS:** `OK` или `FAIL`.

**Пример:**
`ACK 01 42 OK`

## 3. Уровень 2: Проводной интерфейс UART

Поскольку UART — это непрерывный поток байтов, строки из п.2 упаковываются в транспортные кадры (фреймы).

### 3.1. Формат кадра UART
`[START_BYTE] [LENGTH] [PAYLOAD_STRING] [CRC16] [END_BYTE]`

*   **START_BYTE:** Всегда `0xAA`.
*   **LENGTH:** 1 байт. Длина `PAYLOAD_STRING` в байтах (от 1 до 250).
*   **PAYLOAD_STRING:** Сама строка телеметрии или команды из п.2.
*   **CRC16:** 2 байта. Контрольная сумма кадра (алгоритм CRC-16/CCITT-FALSE).
*   **END_BYTE:** Всегда `0x55`.

### 3.2. Правила сборки кадра (на стороне Хаба)
1. Сформировать строку `PAYLOAD_STRING`.
2. Вычислить ее длину `LENGTH`.
3. Вычислить CRC16 для массива, состоящего из `[LENGTH] + [PAYLOAD_STRING]`.
4. Собрать кадр и отправить его побайтово в UART.
*(Примечание: Если длина строки превышает 250 байт, отправка не производится, пишется лог об ошибке).*

## 4. Правила обработки данных (Parser Logic)

Эти правила реализуются на сервере (в Python-парсере) для каждого входящего кадра.

### 4.1. Конвейер валидации (Pipeline)
1. **Прием и проверка кадра UART (Физический уровень):**
   - Ждать `0xAA`.
   - Прочитать `LENGTH`.
   - Прочитать `PAYLOAD_STRING` (ровно `LENGTH` байт).
   - Прочитать `CRC16` (2 байта).
   - Прочитать `0x55`.
   - **Проверка:** Если `CRC16` не совпадает -> сброс, лог `BAD_UART_CRC`.
2. **Парсинг строки (Логический уровень):**
   - Разбить `PAYLOAD_STRING` по пробелам.
   - Извлечь `HEADER`, `DEV_ID`, `TOPIC`, `TIMESTAMP`, `SCHEMA`, `VALUES`.
   - **Проверка:** Если `HEADER` != `TLM` -> сброс, лог `UNKNOWN_HEADER`.
   - **Проверка:** Если `TOPIC` отсутствует в базе (whitelist) -> сброс, лог `UNKNOWN_TOPIC`.
   - **Проверка:** Если `DEV_ID` не найден в таблице `devices` -> сброс, лог `UNKNOWN_DEVICE`.
3. **Валидация схемы (БД):**
   - Запросить `current_schema_version` для данного `DEV_ID`.
   - **Проверка:** Если `SCHEMA` из пакета != `current_schema_version` -> сброс, лог `SCHEMA_MISMATCH`.
4. **Валидация полей:**
   - Запросить `field_definitions` для `(TOPIC, SCHEMA)`.
   - **Проверка:** Попытаться привести каждое значение к типу (float, int, string). Если ошибка -> сброс, лог `TYPE_ERROR`.
   - *(Если полей меньше, чем в схеме, недостающие заполняются NULL).*
5. **Сохранение:**
   - Сформировать JSONB.
   - `INSERT` в `telemetry`.
   - `UPDATE devices` (обновить статус, `last_seen_at`).

### 4.2. Логирование ошибок
Все инциденты (несовпадение CRC, неизвестный Topic, ошибки типов) записываются в лог-файл сервера и/или в таблицу `audit_log`.

## 5. Сквозной пример (Happy Path)

1. **Узел 01** сформировал строку: 
   `TLM 01 sensors 1714132801 v1 25.5 61.8`
   Отправил по ESP-NOW.
2. **Хаб** получил строку (42 байта).
3. **Хаб** обернул её в UART-фрейм, посчитав CRC16 (например, `0x3F2A`): 
   `0xAA [42] [TLM 01 sensors 1714132801 v1 25.5 61.8] [0x3F 0x2A] 0x55`
4. **Python-парсер** прочитал фрейм, проверил CRC16.
5. **Python-парсер** разбил строку по пробелам, проверил `TOPIC`, `DEV_ID`, `SCHEMA`.
6. **Python-парсер** сформировал JSON: `{"temperature": 25.5, "humidity": 61.8}`.
7. **Python-парсер** записал его в БД (таблица `telemetry`).
