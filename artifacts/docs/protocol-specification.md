# Спецификация протокола обмена данными (Protocol Specification)

Настоящий документ описывает «контракт» между компонентами системы: формат данных, правила упаковки, передачи и обработки информации на всех уровнях: от радиоканала ESP-NOW до проводного интерфейса UART.

## 1. Общие принципы (Соглашение)

1. **Кодировка:** Все текстовые данные передаются в кодировке **ASCII** (UTF-8 для расширенных символов, хотя в ТЗ они не требуются).
2. **Разделитель:** В качестве разделителя полей используется символ **пробел (0x20)**.
3. **Пустые поля:** Если значение отсутствует (например, датчик неисправен), передаются два пробела подряд (пустая строка между разделителями).
4. **Контроль целостности:** Все строки и кадры защищены контрольной суммой (CRC). При несовпадении CRC пакет безжалостно отбрасывается.
5. **Регистр:** Заголовки (TLM, CMD, ACK) всегда пишутся заглавными буквами. Остальные данные — строчными (для имен таблиц/команд).

## 2. Уровень 1: Радиоканал ESP-NOW

Обмен по ESP-NOW происходит строками. Максимальный размер полезной нагрузки (Payload) — 250 байт.

### 2.1. Пакет телеметрии (Узел -> Концентратор)
Формат строки: 
`[HEADER] [DEV_ID] [TOPIC] [TIME] [SCHEMA] [VAL_1] ... [VAL_N] [CRC]`

*   **HEADER:** Всегда `TLM`.
*   **DEV_ID:** Идентификатор устройства (например, `01`, `02`).
*   **TOPIC:** Имя таблицы/маршрутный ключ (например, `sensors`).
*   **TIME:** Время формирования посылки (например, `12:00:01`). На текущем этапе может быть заглушкой.
*   **SCHEMA:** Версия схемы данных (например, `v1`).
*   **VAL_1 ... VAL_N:** Значения полей, разделенные пробелами. Количество полей от 1 до 16.
*   **CRC:** Контрольная сумма строки, 4 символа в HEX (например, `A5F3`).

**Пример (2 датчика):**
`TLM 01 sensors 12:00:01 v1 25.5 61.8 A5F3`

**Пример (1 поле пустое):**
`TLM 02 boiler 12:00:05 v1 80.0  1.2 B3C1` *(два пробела между 80.0 и 1.2)*

### 2.2. Пакет команды (Концентратор -> Узел)
Формат строки:
`[HEADER] [DEV_ID] [CMD_TYPE] [ARG_1] ... [ARG_N] [CRC]`

*   **HEADER:** Всегда `CMD`.
*   **CMD_TYPE:** Тип команды (например, `set_interval`, `reboot`).
*   **ARG_N:** Аргументы команды.

**Пример:**
`CMD 01 set_interval 30 A1B2`

### 2.3. Пакет подтверждения (Узел -> Концентратор)
Формат строки:
`[HEADER] [DEV_ID] [CMD_ID] [STATUS] [CRC]`

*   **HEADER:** Всегда `ACK`.
*   **CMD_ID:** ID команды (если применимо).
*   **STATUS:** `OK` или `FAIL`.

**Пример:**
`ACK 01 42 OK C3D4`

## 3. Уровень 2: Проводной интерфейс UART

Поскольку UART — это непрерывный поток байтов, строки из п.2 упаковываются в транспортные кадры (фреймы).

### 3.1. Формат кадра UART
`[START_BYTE] [LENGTH] [PAYLOAD_STRING] [CRC16] [END_BYTE]`

*   **START_BYTE:** Всегда `0xAA` (маркер начала кадра).
*   **LENGTH:** 1 байт. Длина PAYLOAD_STRING в байтах (от 1 до 250).
*   **PAYLOAD_STRING:** Сама строка телеметрии или команды из п.2.
*   **CRC16:** 2 байта. Контрольная сумма кадра.
*   **END_BYTE:** Всегда `0x55` (маркер конца кадра).

### 3.2. Правила сборки кадра (на стороне Хаба)
1. Сформировать строку `PAYLOAD_STRING`.
2. Вычислить ее длину `LENGTH`.
3. Вычислить CRC16 для массива, состоящего из `[LENGTH] + [PAYLOAD_STRING]`.
4. Собрать кадр и отправить его побайтово в UART.

## 4. Правила обработки данных (Parser Logic)

Эти правила реализуются на сервере (в Python-парсере) для каждой входящей строки.

### 4.1. Конвейер валидации (Pipeline)
1. **Прием кадра UART:**
   - Ждать `0xAA`.
   - Прочитать `LENGTH`.
   - Прочитать `PAYLOAD_STRING` (ровно `LENGTH` байт).
   - Прочитать `CRC16` (2 байта).
   - Прочитать `0x55`.
   - **Проверка:** Если `CRC16` не совпадает -> сброс, лог `BAD_FRAME_CRC`.
2. **Парсинг строки:**
   - Разбить `PAYLOAD_STRING` по пробелам.
   - Извлечь `HEADER`, `DEV_ID`, `TOPIC`, `TIME`, `SCHEMA`, `VALUES`.
   - **Проверка:** Если `HEADER` != `TLM` -> сброс, лог `UNKNOWN_HEADER`.
   - **Проверка:** Если `TOPIC` отсутствует в базе (whitelist) -> сброс, лог `UNKNOWN_TOPIC`.
   - **Проверка:** Если `DEV_ID` не найден в таблице `devices` -> сброс, лог `UNKNOWN_DEVICE`.
3. **Валидация схемы:**
   - Запросить в БД `current_schema_version` для данного `DEV_ID`.
   - **Проверка:** Если `SCHEMA` из пакета != `current_schema_version` -> сброс, лог `SCHEMA_MISMATCH`.
4. **Валидация полей:**
   - Запросить в БД `field_definitions` для `(TOPIC, SCHEMA)`.
   - **Проверка:** Если количество элементов в `VALUES` не совпадает с ожидаемым -> лог `FIELD_COUNT_MISMATCH`, но **не сбрасывать** (а попытаться записать то, что есть, заполнив остальные NULL).
   - **Проверка:** Попытаться привести каждое значение к типу, указанному в `field_definitions` (float, int, string). Если ошибка -> сброс, лог `TYPE_ERROR`.
5. **Сохранение:**
   - Сформировать JSONB.
   - `INSERT` в `telemetry`.
   - `UPDATE devices` (обновить статус, `last_seen_at`).

### 4.2. Логирование ошибок
Все инциденты (несовпадение CRC, неизвестный Topic, ошибки типов) записываются в лог-файл сервера и/или в таблицу `audit_log`, чтобы разработчик мог отследить причину потери данных.

## 5. Сквозной пример (Happy Path)

1. **Узел 01** сформировал строку: 
   `TLM 01 sensors 12:00:01 v1 25.5 61.8`
   Посчитал CRC (A5F3) и отправил по ESP-NOW: 
   `TLM 01 sensors 12:00:01 v1 25.5 61.8 A5F3`
2. **Хаб** получил строку (40 байт).
3. **Хаб** обернул её в UART-фрейм: 
   `0xAA [40] [TLM 01 sensors... A5F3] [CRC16] 0x55`
4. **Python-парсер** прочитал фрейм, проверил CRC16.
5. **Python-парсер** разбил строку по пробелам, проверил `TOPIC`, `DEV_ID`, `SCHEMA`.
6. **Python-парсер** сформировал JSON: `{"temperature": 25.5, "humidity": 61.8}`.
7. **Python-парсер** записал его в БД (таблица `telemetry`).
8. **Python-парсер** отправил ACK обратно (если требуется).
