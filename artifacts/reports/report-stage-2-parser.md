# Отчет об испытаниях: Этап 2 (Бинарный UART и Python-парсер)

**Дата:** 2026-11-10
**Статус:** ✅ Успешно завершено
**Расположение артефактов:** `src/mcu/master/`, `src/backend/parser_console.py`

## 1. Цель этапа

Проверить способность Python-скрипта читать бинарный поток данных из COM-порта (формат UART-фреймов), корректно находить границы кадра (`0xAA` ... `0x55`), проверять контрольную сумму (CRC-16/CCITT-FALSE) и извлекать текстовую полезную нагрузку.

## 2. Методика испытаний

1. **Прошивка Хаба (master):** Вывод в порт переведен из режима текстового HEX-дампа в режим отправки «сырых» байтов (`Serial.write`). Это сделано для того, чтобы Python мог читать реальные бинарные данные, а не их текстовое представление.
2. **Скрипт (Python):** Написан `parser_console.py`, который использует библиотеку `pyserial` для чтения потока, накапливает данные в буфере, ищет стартовый байт `0xAA`, сверяет длину и проверяет CRC.
3. **Среда:** ПК с Windows 10, Python 3.x, ESP32 (Master), ESP32 (Slave).

## 3. Результаты испытаний

### 3.1. Вид бинарного потока в текстовом мониторе (Ожидаемый хаос)

При попытке прочитать бинарные данные в текстовом мониторе Arduino IDE, мы видим «кракозябры». Это доказывает, что данные уходят именно как бинарный поток, а не как текст.

```text

```

### 3.2. Работа Python-парсера (Успешная десериализация)

Скрипт `parser_console.py` успешно выловил кадры из бинарного мусора, проверил контрольные суммы и извлек строки.

**Фрагмент лога Python:**

```text
[17:29:53] Открываю порт COM4...
[17:29:53] Ожидание данных... (Ctrl+C для выхода)

[17:29:58.557] [+] CRC OK | TLM 01 sensors 4 v1 25.0 49.7
[17:30:03.568] [+] CRC OK | TLM 01 sensors 9 v1 25.7 56.7
[17:30:08.557] [+] CRC OK | TLM 01 sensors 14 v1 25.9 47.7
```

### 3.3. Верификация по времени (Синхронизация Slave и Парсера)

Сравнение логов Узла (Slave) и Парсера показывает минимальную задержку:

- **Slave:** `17:29:58.559 -> TX: TLM 01 sensors 4 v1 25.0 49.7`
- **Parser:** `[17:29:58.557] [+] CRC OK | TLM 01 sensors 4 v1 25.0 49.7`
  _(Задержка на уровне нескольких миллисекунд, что подтверждает высокую скорость магистрали)._

## 4. Выводы

1.  **Алгоритм CRC-16/CCITT-FALSE полностью совместим.** Python и C++ считают одинаковую контрольную сумму для одних и тех же байтов. За время теста (более 20 пакетов) не зафиксировано ни одной ошибки `CRC FAIL`.
2.  **Алгоритм поиска кадра (State Machine) работает корректно.** Python правильно игнорирует текстовый мусор и точно определяет границы пакета по байтам `0xAA` и `0x55`.
3.  **Данные готовы к записи в БД.** Извлеченные строки (например, `TLM 01...`) идеально соответствуют спецификации протокола v1.1. На следующем этапе они будут распарсены на ключ-значение и записаны в PostgreSQL.
